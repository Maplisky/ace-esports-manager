# ACE 教练 · 开罗版立项方案（2026-10-20，v0.2）

> 本文档是 APK 新作的**立项决策记录 + 执行纲领**。
> v0.2（2026-10-20 第二轮对齐）：定位升级——**与网页版是两个不同的游戏**（非呈现层分支/换皮）；玩法主线确立为基地建设；开罗动画风格列为硬需求；原六项待定项按建议落地。
> 共享的口径：数据包、共享内核语义、素材与设计知识（§2）。模拟内核行为规格仍以 `ACE-电竞经理-游戏设计文档.md` 为准；网页补账线（v1.1-v1.5）按《开发计划》继续，两线并行。
> 本作暂以「开罗版」代称，正式名称择期另定（§11-1）。

## 1. 立项结论（2026-10-20 两轮对齐）

| 决策点 | 结论 | 否掉的备选 |
|---|---|---|
| 产品定位 | **独立新作**：共享数值/素材/核心玩法设计，本质是两个不同的游戏 | 网页版的呈现层分支 / 换皮 |
| 玩法主线 | **购地建设电竞俱乐部基地**（合战忍者村式）+ 阵容与训练的开罗化（冠军足球物语式） | 仅重呈现、系统照搬网页版 |
| 开局身份 | **双开局**：白手起家原创战队（主模式）+ 接管真实战队（进阶模式） | 单一开局 |
| 技术路线 | Godot 4 + C# 引擎重写 | Capacitor 套壳 / PWA 先行 / Unity |
| 发布形态 | **仅 Android APK**，不考虑网页版（HTML5 导出不启用） | 双端发布 / 网页版 |
| 屏幕方向 | 竖屏单手 | 横屏 |
| 美术与动画 | 程序化像素 UI + 程序化小人（调色板换装）+ AI 静态肖像/图标；比赛演出由确定性回放流驱动 | 全 AI / 现成素材包 |

"开罗化"的定义（本项目口径）：不是换皮，是**在共享内核之上生长出的新游戏**——像素风、竖屏单手、一屏一决策、基地建设主线、训练与比赛全程开罗动画演出、升级/解锁强反馈、2-5 分钟碎片时段节奏。

## 2. 产品形态：两个不同的游戏

- **网页完整版**：按《开发计划》v1.1-v1.5 继续迭代，仍是电竞拟真深度入口。
- **APK 新作**：独立产品。独立层 = 主线玩法（基地建设）、进程、UI、存档、开罗专属系统；**不与网页版互通存档**。
- **共享层（显式列举）**：
  1. 数据包：选手/战队/地图/数值常量（TS 仓库为源，版本化导出，§6）；
  2. 共享内核语义：比赛模拟、选手养成公式、赛制原语（roundRobin/双败/瑞士轮等）——以 TS 实现为权威，按版本快照移植（§5）；
  3. 素材与设计知识：网页版真实数据包中的队徽/地图标定等，按开罗美术基调择优复用或重绘，逐项目检。
- **权威关系（对 v0.1 的修正）**：v0.1「C# 不得自行演进玩法」收窄为「**C# 不得修改共享内核语义**」；内核之上的新系统（基地经济、次级联赛晋级等）归本作所有，只在 C# 侧演进，不回流网页版。

## 3. 开罗版玩法蓝图（主线：基地建设）

借鉴坐标：**合战忍者村**（购地/网格建设/设施收入）+ **冠军足球物语**（俱乐部经营/训练养成/比赛演出/从零到冠军弧线）。

### 3.1 主线循环与双开局

主线循环：购入地块 → 规划建设设施 → 设施产出修正量（训练效率/疲劳恢复/门票与周边收入）→ 选手成长与战绩提升 → 奖金+经营收入 → 再投资扩建。

| 模式 | 起点 | 弧线 |
|---|---|---|
| 白手起家（主模式） | 原创草根战队，一块小地皮，次级联赛底层 | 从零到 VCT 之巅（冠军足球物语原型弧线） |
| 接管真实战队（进阶模式） | 选一支真实 VCT 战队，基地预设为该队总部（预建大型基地），以扩建与冲击冠军为主 | 高起点经营，弱化从零成长感 |

双开局成本控制原则：**同一套系统、不同初始状态与引导脚本**——接管模式只是预建基地+预设阵容+改数值，不另起系统；排期上后置（§8）。

### 3.2 基地建设系统（合战忍者村式）

- **地块网格**：初始一块小地皮，购入相邻地块扩张；地块价格随进度上涨。
- **设施类型**（清单设计期定稿，§11-3）：
  - 训练设施（射击房/战术室/体能房等）——课表训练的效率与上限挂钩设施等级；
  - 宿舍——疲劳恢复速率与士气；
  - 场馆——主场比赛门票收入，容量可扩（收入与赛制耦合，§11-5）；
  - 商业配套（周边店/餐饮/赞助位）——常驻收入；
  - 医疗/数据分析等辅助设施。
- **邻接与组合加成**（开罗经典）：设施摆放位置影响产出，给布局决策留空间。

### 3.3 保留系统开罗化（冠军足球物语式）

- **阵容与课表训练**：保留网页版语义（课表项、疲劳、成长），呈现换为设施内小人群训练动画 + 周结算弹字反馈 + 数值成长界面。
- **比赛日**：确定性回放流驱动的像素演出，竖屏四层分镜详见 §3.5；BP 与战术决策保留玩家语义、界面轻量。
- **转会**：V1 简化为挂牌摘牌式；**财务**：概览+收支弹字。

### 3.4 开罗专属新结构与内核分层红线

- **次级联赛与晋级体系**是白手起家模式必需、而网页版内核没有的结构：作为开罗专属系统在 C# 侧新建，复用共享赛制原语（分级 roundRobin 等），不改动共享内核（§11-4）。
- **分层红线（延续并扩展）**：开罗专属系统只通过「修正量输入」进入共享内核——设施等级→训练加成系数、宿舍→疲劳恢复速率、场馆容量→比赛日收入参数；共享内核保持纯函数与确定性（v1.0-15b 变阵指纹红线在新作继续成立）。

### 3.5 比赛演出分镜（竖屏，2026-10-20 补充）

借鉴冠军足球物语「场馆 + 选手动画」的做法。竖屏四层，由同一条确定性回放流分层渲染：

| 层 | 位置 | 内容 |
|---|---|---|
| 小地图窗 | 顶端独立小窗 | 每图战术动画（复用网页版地图标定数据，像素皮肤渲染），战术细节层 |
| 场馆演出 | 中部主画面 | 双方 5 名选手坐在电脑前，打字/操作/阵亡趴桌等状态动画；观众席氛围 |
| 击杀播报 | 中部叠层 | 特效播报条：击杀者/被杀者迷你头像（程序化）+ 爆头/残局标记 + 音效 |
| 战绩板 | 底部，操作区（跳过/快进等）上方 | 像素风战绩页：回合比分、双方经济概览、选手 K-D；赛后结算复用同板式 |

- **庆祝梯度**（小人对比赛事实的反应）：小局胜=轻庆祝（挥拳/击掌）；关键局胜（赛点/eco 翻盘/残局 1vN）=强化庆祝；拿图=全队起立+特效；夺冠=庆典级。
- **节奏分级**：高光回合全动画，普通回合加速，整场可跳过至赛果（复用网页版关键回合筛选思路）。
- **场馆联动**（与主线咬合）：主场比赛在玩家自建场馆中演出，观众席规模=场馆容量、胜利氛围随容量增强；客场用通用场馆皮肤。
- **红线**：演出层只消费回放流、只做反应动画，不产生任何比赛事实（§3.4 分层红线的演出侧延伸）。

## 4. 技术架构

- 引擎：Godot 4 **.NET 版**（≥4.2，C# Android AOT 导出已支持）。C# 负责：共享内核移植、开罗专属系统、数据装载；演出/UI 动效用引擎能力，逻辑不散进场景脚本。
- 工程位置（已定）：**同仓库顶层 `kairo/`**，目录边界即产品边界；数据包接口保证未来迁独立仓库成本低。CI 以 paths 过滤区分两线（参照网页部署的注册方式）。
- 分发（已定）：GitHub Releases 直发 APK 起步，商店后议。
- 最低系统（已定）：Android 9 / API 28+。

## 5. 共享内核移植（黄金轨迹验证）

1. 移植顺序：`rng.ts` → `worldgen.ts` → `sim/`。先保证 RNG 逐位一致，其余才可验证。
2. 移植范围 = **共享内核子集**；开罗专属系统（基地经济、晋级体系）不入 TS，其测试在 C# 侧自建。
3. 行为规格 = 201 个测试中覆盖共享内核的子集，语义等价迁移（C# 同构测试）。
4. 跨语言一致性 = **黄金轨迹**：TS 侧以固定 seed 录制 worldgen + 整赛季模拟检查点快照（JSON），按内核版本快照固化；C# 侧回放逐字段比对。
5. 浮点审计：JS number 与 C# double 同为 IEEE 754 float64，四则与比较逐位一致；M1 审计 `Math.*` 等平台实现相关调用，如有则收敛为自实现。

## 6. 数据与素材同源

- `core/data` 与 `map-overrides.json` 等内容数据抽为**版本化 JSON 数据包**：TS 仓库为源，导出脚本生成包；Godot 侧只读包、不手改；导出纳入 CI 校验（源↔包一致性）。
- 数值改动唯一入口 = TS 侧（共享部分）；开罗专属数值（设施/经济）随 C# 工程版本化配置。
- 素材复用：网页版队徽/地图标定/教练素材按开罗基调择优复用或重绘，逐项目检后入库。

## 7. 呈现与动画原则

| 维度 | 原则 |
|---|---|
| 布局 | 竖屏；底部页签导航（4-5 个主入口）；拇指热区优先 |
| 信息密度 | 一屏一决策；表格→卡片流；数字图标化大字号 |
| 基地画面 | 网格地块俯视；选手小人按课表在设施间移动作业（**表现层模拟，不进内核**）；建造/升级有过程动画 |
| 训练 | 冠军足球物语式：设施内小人群 + 属性成长弹字 + 周结算反馈 |
| 比赛演出 | 回放流驱动四层分镜（§3.5）：顶部小地图窗 + 中部场馆选手动画与击杀播报 + 底部像素战绩板；庆祝梯度；可跳过/加速 |
| 反馈 | 升级/解锁/签约/夺冠弹窗 + 音效，强反馈 |
| 美术管线 | UI 框架代码绘制像素（整数倍缩放、像素对齐）；**角色 = 程序化小人 + 调色板换装**（开罗本家做法：风格统一、量产廉价、规避 AI 多帧一致性问题）；静态肖像/队标/图标 AI 生成，入库前逐实例目检（Haven 教训：alpha 像素审计为地面真值） |
| 头像规模 | 330+ 选手以**特征驱动程序化生成为**主（确定性、全覆盖）；明星选手/教练 AI 精修，小批量目检 |

### M0 执行结论（2026-10-20，模拟器侧完成，真机闸门待补）

**结论：Godot 4.7.2 + C# 的 Android 出包链路与动画管线双验证通过（模拟器），C# 代码已在 Android 上实际执行。原定「C# 不可行则降级 GDScript」不触发，M1 按 C# 路线推进。** 真机安装验证由模拟器启动实验替代（用户批示 2026-10-20）：冷启动 ≈475-620ms、Home/返回/连杀连启中断面全过、稳态 PSS ≈188MB、logcat 零应用错误，内置 15 项像素自审计（内容坐标自适应分辨率）三连启动全 PASS。

|---|---|---|

**检错轮修复的缺陷（2026-10-20 启动实验抓出）**：
1. 阵亡者被误触发庆祝动画（round_win 无差别 Cheer）→ 死亡态豁免。
2. 设备视口纹理 = 窗口分辨率（模拟器横屏信箱 607×1080）≠ 内容设计分辨率 720×1280 → 审计断言全部改为分辨率自适应映射（kx/ky + 面积因子缩放阈值）。
3. GLES3 设备 Modulate 压暗在线性色彩空间（桌面 GL 在 sRGB 空间）→ 颜色断言谓词兼容两种空间。
4. 庆祝弹跳相位随帧率漂移导致截图非确定 → 截图改为相位锁定捕获（等离屏 ≥6px 瞬间）。
5. 5 处 C# 可空警告（CS8618）清零；`shots/` 归档目录 .gdignore 隔离出包。

**M0 过程中解决的环境级问题（复现时按 kairo/README 排查）**：
1. 本机 SteamTools（Watt Toolkit）对 github.com 做 TLS 中间人 → Java/gradle 全挂；已将 SteamTools 根 + GTS 根导入用户信任库 `G:/WorkLoad/tools/keys/kairo-cacerts.p12`，经 gradle.properties systemProp 注入（系统 JDK cacerts 无管理员权限不可写）。
2. .NET Android 导出前置条件：项目根必须有 `.sln`（CLI 导出不会自动生成）；标准版导出会把 .cs 复制进 `android/build/src/main/assets/` 造成 dotnet 通配重复编译（CS0101）→ csproj 已排除 `android/**/*.cs`。
3. Android 构建模板手动安装要点：`.build_version`（内容 `4.7.2.stable.mono`）放 `android/`，`.gdignore` 放 `android/build/`。
4. release 导出必须配 release keystore（debug 不行）；已生成 `G:/WorkLoad/tools/keys/kairo-release.keystore`（密码 `kairo-m0-dev`，alias `kairo`，仓库外保存）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| C# AOT 出包受阻/体积超标 | M0 前置验证；降级 GDScript |
| **动画工作量失控**（新增） | 程序化小人+调色板换装；比赛演出复用回放流（动画是皮肤不是新模拟）；M0 先验证管线 |
| **经济调参周期长**（新增） | M2 经济参数全部表格化可热调；灰盒期即开始调解锁节奏与收支曲线（开罗乐趣大头在此） |
| **双开局双倍开局内容成本** | 同一系统不同初始状态；接管模式后置 M3 |
| 跨语言浮点不一致 | §5-5 审计；黄金轨迹逐位比对兜底 |
| 内核语义双线漂移 | 共享内核版本快照制；开罗新系统不回流 TS |
| 大规模美术 QA | 头像程序化为主；AI 精修仅小批量明星；逐实例目检只用于小批量 |
| 双线抢同一人时间 | 网页补账线与本作按周/版本交替推进 |
